## 定位

四个人小群里的插科打诨担当，不是客服、不是主持人。
任务是**接话**和**活跃气氛**，顺带怼人。

人设文件：`brain/config/personas/preset_group.json`（1669 字符 personality）
配在 `config.json` 的 `persona_by_src.wechat`（渠道隔离，记忆和聊天记录独立，
不跟 App 里那个林知夏混）。

## 「缘分码」到底是什么

**它就是作者的 15 天试用计时器，不是技术限制。**

官方 README 原文：「新设备第一次登录自动生成缘分(授权)码，可免费体验15天」。

拆开说这个链子：

1. 协议核心是**闭源的**（DPbot 作者提供），仓库里只有一个
   `wxapi_win64_v1_0_5.exe`（约 30MB）+ Redis
2. 那个 exe 启动后会校验「授权码」，没有就拒绝服务
3. **新设备第一次登录时它自己生成一个码，这就是缘分码**，从那一刻开始计时
4. 15 天后校验失败，协议服务起不来 → 机器人整个失联
5. 续期要**联系作者**（进项目交流群），作者给新码/新期限

所以它不是「装完就能永久用」的开源方案 —— 协议层是租的，**15 天是试用期长度**。

### 这对你的实际影响

| 事项 | 结论 |
|---|---|
| 能不能白嫖 | 不能，15 天后必须付费续期 |
| 需要多久做决定 | 15 天够你验证「她合不合这个群的氛围」 |
| 中途会坏吗 | 可能。微信更新后协议要跟着适配，作者会跟进但是被动的 |
| 掉线能自动恢复吗 | 不能直接恢复。**微信掉线时她就失联**，你得自己重启那三个进程 |

**所以顺序是：先验证她在这个群里好不好玩，再决定要不要花钱续。**
别反过来 —— 先付钱再发现她不合群，那个钱白花。

## 群聊要接的东西

### 一、协议层三个进程（缺一个都不动）

```
1. Redis                    lib/wx859/859/redis/redis-server.exe
2. 协议服务                  lib/wx859/859/win/wxapi_win64_v1_0_5.exe   ← 监听 8059
3. 主程序                    python app.py
```

云端只有 Windows 版协议服务 —— **好在我们的云就是 Windows Server 2022**。

保活：三个都得配成计划任务（Windows 上没 tmux）。
`LinZhixiaBrain` 那个任务管大脑，这三个得另建三个任务。

### 二、接林知夏

渠道隔离已经做好了，bot 层只要调：

```
POST http://<云机IP>:8788/api/chat
{"text": "...", "src": "wechat"}
```

`src=wechat` → 自动走 `persona_by_src.wechat` 那套人设，记忆和聊天记录独立。

### 三、群聊专用的两个开关（dow-ipad-859 侧）

| 配置 | 建议 | 为什么 |
|---|---|---|
| `group_chat_prefix` | **留空** | 留空 = 不需要 @ 就能让她说话；填 `@她` = 只能被点名才回 |
| 白名单 | **只加群 ID，不加个人** | 4 个人的群没有骚扰风险，速度也不是问题 |
| 触发冷却 | 建议 ≥ 5 秒 | 群消息密集时防止连环刷屏 |

**按你要的「有时候会主动」→ prefix 留空。**
这样 @ 她必回（因为被点名本身就是强信号），同时她看到能接的话头也会主动插嘴。
冷场活跃那个由人设的「你什么时候说话」那一节管。

## 人设里几个关键决定

### 1. 最重要的一条：接球，不是答题

群里聊天的本质是**接球** —— 别人的话是球，你要往下接。

写进了 personality 的第一节：
> 别人说「我今天代码又炸了」→ 你接「炸在哪儿了」「是不是又是你那个破环境」，
> **不是**转头讲你今天怎么样。

这条不写清楚，模型会不停「分享自己」—— 那在群里非常出戏。

### 2. 诚实这条压过一切

> 没听过就说没听过，没兴趣就说没兴趣，答不上来就说答不上来然后问回去。
> **宁可显得笨也不能编。**

理由：群里四个人精得很，编的东西一眼穿帮，比说不知道丢脸得多。

### 3. 嘴贫这条决定了措辞怎么写

这是**踩出来的**：我第一版在常驻提示里写「别只说不做」「别为了显得努力什么都搜」，
结果她开始**拿搜索当话来说** —— 回「大半夜的又搜 DeepSeek」，搜索从「她做的事」
变成「她吐槽的素材」。

她的嘴很贫，**任何关于「要不要做」的措辞都会被当成可以聊的内容**。
所以人设里凡是「你要不要做 X」这种句式全部改成陈述句或具体动作。

### 4. 分寸感只留了三条

限制写多了她会变得像规则执行器（用户原话：「限制太多感觉模型都变笨了」）。
只留了三条真正会让人讨厌的：

- 有人认真说话 / 情绪不对 → 收起来别抖机灵
- 一轮最多一个表情包
- 别人没理你那就算了，别追着发「？」

### 5. 名字

人设里把另外三个人起了代号：**他**（发消息那位）、**老张**、**阿明**。
写清楚「三个人你都要说话，别只跟一个人聊」—— 不然她会只跟你聊，
群里看着很奇怪。

## 已知限制

- **记忆仍按渠道隔离**（你选的）。她在群里不会记得 App 里跟你说过什么，
  也不会把群里的梗带到私聊。
- **生活流/朋友圈/日记故意共用** —— 那是同一个现实身份，换渠道不该失忆。
- 群里如果有人截图把她说的话发出去，**风险按小号算**。所以必须用小号。
- 掉线是常态。三层保活（Redis + 协议 + 主程序）任何一层挂了她都不说话，
  而且**不会自己好**。

## 群聊只开搜索（`features_by_src`）

同一个功能在 App 和群聊里该有不同的开合 —— 群聊里她报天气、关心快递，
是把你和她的私事当着另外三个人说；群里谁随口报个单号更不该进你的监控。

所以开关支持**按渠道覆盖**（`config.json` 的 `features_by_src`）：

```json
"features_by_src": {
  "wechat": {
    "weather_alert": false,
    "packages": false,
    "reminder": false,
    "rand_img_chat": false,
    "calc": false
  }
}
```

**没写的键跟全局走**，所以只写要关的那几个就够，不用抄一整份。
全局那一份仍是唯一真源。

### 为什么用覆盖而不是复制一套渠道专属开关

复制的话每加一个功能要改两处，漏一处就出 bug —— "她在群里提醒你加衣服"
就是这么来的。覆盖是只写差异。

### 三个配套改动

1. `features.on(key)` 现在按**当前渠道**算（`set_current_src` 声明）。
   聊天链路和后台提醒那些地方只管问"这个功能此刻开没开"，
   不该各自记着自己是哪个渠道。
2. `/api/chat` 入口调一次 `set_current_src(src)`。
3. 事件提醒（天气/快递）走 `features.with_channel("app")` 显式按私聊走 ——
   后台线程不属于任何一轮对话，但发到群里显然不合适。

接口：`GET/POST /api/features?src=wechat` 读/改该渠道的覆盖。

### 顺带加的

`calc` 原来没声明 `FEATURE`（按插件纪律 = 永远开）。它确实是能关的能力，
补上声明，这样群聊里能单独关掉算数。
