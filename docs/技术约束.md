# 技术约束 · 为什么必须这么做

这份文档记的是**踩过的坑和它们背后的设计约束**。改代码前先读，
不然很容易把某个看起来多余的绕dle又加回去。

---

## 一、微信 4.x 的无障碍闸门

### 现象
`wxauto4` 报「未找到已登录的客户端主窗口」，而窗口枚举明明能看到
`Qt51514QWindowIcon`，`FindWindow('Qt51514QWindowIcon')` 也确实找得到主窗口。
卡在拿到窗口之后遍历控件这一步 —— **UIA 树里 `mmui::*` 元素数是 0**。

### 原因
> **微信 4.x 是自绘 UI，Qt 只在检测到无障碍客户端时才构建完整控件树。**
> 闸门关着时 `WM_GETOBJECT` 只返回 Qt 空壳。

这是 Qt 的机制，不是微信坏了。

### 解法
`vm/zx_uia_wake.py`，四步：
1. 置 `SPI_SETSCREENREADER`
2. `OpenProcess` 找加载 `Weixin.dll` 的 PID
3. 写闸门字节 1
4. **校验 `mmui::` 控件是否真的物化，没出现就回滚**

第 4 步不能省：不校验的话「以为激活了其实没激活」和「真的没激活」
表现完全一样。

### 闸门 RVA 会随版本漂移
社区实测 `0x0AE2B0C8` 对应微信 `203.0.113.10`，本项目用的是 `203.0.113.10`。
**但代码内置 DLL 反汇编扫描**：找 `qt.accessibility.core` 字符串 → 找 RIP 相对
引用 → 匹配 `cmp byte [rip+disp32], 0` 指令模式。
所以**微信升级不用改代码**，扫描自己找。

### 🔴 上游方案有三个真 bug（已修，别改回去）

| # | Bug | 后果 |
|---|---|---|
| 1 | RIP 基址**漏加指令长度**（`insn_rva + disp` 应为 `insn_rva + insn_len + disp`）| 每个命中偏 1 字节，一个都匹配不上 |
| 2 | 位移**有符号**未按 32 位回绕 | 指令在目标之下时算出**负 RVA**，全丢弃 |
| 3 | 普通形式 disp **读错一字节** | 普通形式全漏；REX 形式碰巧对 |

第 2 个在 `_scan_gate_candidates` 的 `cmp_rva + 7 + disp` 里也有一份，
**而那行算的正是闸门字节地址本身** —— 不修就永远找不到闸门。

**判断有没有改坏，用不变量而不是「与旧实现一致」**：
旧实现本身是错的（每命中报两次，100 个种下报 151）。
判据是「种 N 条 → 恰好命中 N 条，且 RVA 是指令真实起点」。

### 🔴 性能：必须用 `bytes.find()` 跳跃，不能逐字节循环
原实现 `for index in range(len(raw)-7)` 逐字节扫每个可执行段：
400 KB 要 0.024s，微信 DLL（几百 MB）**≈ 40 分钟**。
表现就是「双击后卡在第 3 步不动」。改成 `raw.find(b"\x8d")` 跳跃后
40 MB **0.00 秒**（差 80 倍以上）。

## 二、微信 4.x 只给「屏幕上露出来的那部分」注册 UIA 控件

`wxauto4/param.py` 第 57-60 行**明文**写着：

```python
# 由于4.x版本客户端的ui机制是显示的部分才注册uia控件
# 所以尽可能拉大窗口显示更多消息来提高判断容错
CHAT_WINDOW_SIZE = (1200, 4800)
```

所以：
- **UIA 树节点少是正常现象**，不是坏了
- 微信窗口太小 → 控件树建不全 → 表现为 attach 失败

🔴 **教训**：`.pyd` 里挖字符串挖不出来的时候，先去看同包的
`param.py` / `__init__.py` **明文**。配置常量几乎总在明文里，
只有实现逻辑在编译模块中。

## 三、pywin32 在 PYTHONPATH 目录下 import 不到

`from wxauto4 import WeChat` → `ModuleNotFoundError: No module named 'win32gui'`，
**但文件就在 `pkgs\win32\win32gui.pyd`（223KB）**。

原因：pywin32 的 wheel 把 `.pyd` 放在 `win32\`、`win32\lib\`、
`pythonwin\`、`pywin32_system32\` 子目录，靠 site-packages 里的 **`.pth` 文件**
把目录加进 `sys.path`。

🔴 **`.pth` 只在真 site-packages 生效，PYTHONPATH 目录无视** → 谁都不加 → 必然找不到。

✅ 解法：**在要 import 的那个进程里显式加这四个子目录**。
`zx_launcher.py` 顶部就是这么做的。

⚠️ 别指望 `sitecustomize.py` —— 它在这个进程里**不生效**（因为它是被
`sys.path.insert` 加进去的，`site` 早就跑完了）。

## 四、子窗口模式（`listen: true`）实测不可靠

`AddListenChat` 听起来能免抢窗口，实测：
- 同一段代码两次跑，一次读到 2 条、一次读到 **0 条**
- 传的回调从头到尾 **fired 一直是 0**

所以**保持 `false`**，走主窗口轮询。代价是会把微信切到那个对话（占前台），
用 `pause_when_away: true` 缓解：前台不是微信就这一轮完全不碰微信。

**不抢窗口 + 可靠**在 wxauto 这条路上做不到，只能换非 UI 级接入（Hook/协议）。

## 五、🔴 会话隔离：判断力矩，别重复踩

wxauto4 靠 UIAutomation 驱动**真实界面**，**只能看见自己所在会话的窗口**。

推论：
- SSH 里跑桥接**必然失败**，这不是 bug
- 计划任务、`Win32_Process.Create` 都不跨会话
- **唯一可靠的办法是用户在真桌面双击图标**

### 🔴 但别把它当根因
曾在这里误判过一次：用户**亲手双击**后同会话**仍然失败** → 会话不是原因，
之前 SSH 侧看到的「0 个窗口」只是**跨会话视角的正常现象**。

> **别拿「观测不到」当「不存在」，也别拿「在错的地方测出来的失败」当判据。**

判断哪个是真桌面要问对问题：`query session` 里「已连接」的不一定对，
**有 `explorer.exe` 的那个才是真桌面**。会话编号会重排，别拿上次的推理。

## 六、🔴 子进程输出必须落盘

桥接拒绝运行时会把原因 print 出来（连不上大脑 / 身份不符 / 群名对不上），
但 `subprocess.Popen(args, cwd=..., env=...)` **没接 stdout** →
控制台一关证据归零，`launcher.log` 只剩「exited with code 1」，**不指名任何原因**。

✅ 现在 `zx_launcher.py` 用 `stdout=PIPE, stderr=STDOUT` + `_pump` 线程
逐行 tee 到控制台**和** `bridge.log`。

🔴 **必须边读边转**：只 `p.wait()` 不 drain，64KB 管道填满会把子进程卡死。

🔴 `TextIOWrapper(errors="replace")` 不能用严格解码 —— 桥接 print 中文，
一个坏字节杀掉这个线程，日志又变回静默失败。

## 七、🔴 存活检查：「有响应」不等于「能用」

`check_tunnel()` 只判**有没有响应**，`HTTPError`(401) 也算活着
（这是对的 —— 401 证明请求走完了整个来回，隧道是通的）。

但 **401 会一路放行到桥接才炸**。曾因此排查了很久：
启动器说「隧道 OK」，桥接说「连不上大脑，401」。

> **「隧道通」和「token 对」是两件事，必须分开验。**

## 八、token 有三份，别搞混

| 位置 | 角色 |
|---|---|
| `C:\Vigil\config\config.json` 的 `brain_token` | **唯一权威**（12 位）|
| `C:\zx\wxbridge.local.json` 的 `brain_token` | 桥接的副本 |
| `zx_key` | 完全另一回事，**别拿来当 token** |

🔴 **空字符串一定失败**。本项目发生过：`brain_token` 是空的，
桥接 11 秒静默退出，群里表现为「她一声不吭」。

✅ 修法：**机器抄送，不手打**。云端读 → base64 传 → 写入 → 读回校验 →
再用云端自己打一次 `/api/plugins?token=` 验证 200。
手打正是它当初走偏的原因。

### 云端配置有两份，只有一份活着
`paths.py` 按自身所在目录算 → 运行时读 `C:\Vigil\config\`。
`C:\Vigil\brain\config\` 是**废弃副本** —— 读错那份会得出
「token 从来没变过」这种错误结论。

## 九、大脑接口的两个细节

- **token 走 query 参数**（`?token=xxx`），**不是 header**。键名是 `brain_token`
- **云端 Python 不在 PATH**，在 `C:\Vigil\.venv\Scripts\python.exe`
  （从 `server_run.bat` 里读出来的，不是猜的）
- 本机有代理，urllib 会去撞它 → `build_opener(ProxyHandler({}))` 显式禁掉
- **云端 8788 不对公网开放**（22 端口的 SSH 能连不代表 API 端口也能连）
  → 桥接机从公网直连会超时，**这是正常的**

## 十、🔴 远端改配置的通用规矩

两台机器的控制台都是 **codepage 936（GBK）**：

- **别在远端 `print` 中文** —— 会 `UnicodeEncodeError`（emoji 直接炸），
  即使不炸也全是乱码。**正确做法：远端写 UTF-8 文件 → sftp 取回 → 本机解码**
- 要打印中文名就用**码点转义**（`\uXXXX`），码点不会被任何代码页改写
- **按名字判断归属，绝不按大小** —— 曾差点把 849 字节的
  `宝塔面板.lnk`（服务器自带）当残留删掉
- `assoc` / `ftype` 是 cmd.exe 的**内部命令**，不是独立 exe
  → `subprocess.run(["assoc", ...])` 报 `FileNotFoundError`，必须 `cmd /c assoc`
- ⚠️ **别套 `powershell -Command "& {...}"` 调解释器**（三层引号已失败多次），
  直接 `'"C:\\...python.exe" "C:\\zx\\x.py"'`

## 十一、`.cmd` 文件的三个坑

1. **中文 + 纯 LF + goto 标签** = cmd.exe 经典失败组合，
   症状是「双击完全没反应」。→ 易碎逻辑搬进 `.py`，`.cmd` 缩成纯 ASCII
2. **写 `.cmd` 必须二进制模式 + 显式 `\r\n`**（文本模式的换行翻译会把 CRLF 又搞坏）
3. **`.bat` 的扩展名关联可能是坏的** → shell 弹「选择打开方式」。
   ✅ 根治：**改用 `.lnk`**，shell 直接执行目标，根本不做扩展名查询

## 十二、桥接本体的返回值约定

`main()` 返回非 0 时 `launcher.log` 只记 `exited with code N`，**不指名原因**。
所以 `connect()` 里所有会失败的地方都必须：

- **接住异常**并 print 人话（`WeChat(ads=False)` 是**抛**异常，不是返回 False）
- **返回 False** 让上层按「连不上」处理，而不是裸 traceback 穿出去
